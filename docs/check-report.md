# 運行指示書管理アプリ：資料チェック報告

確認日：2026年10月9日

## 確認範囲と現状

添付の operation-instructions-design-v1.md を設計資料として確認した。資料内の新規リポジトリ作成や外部サービス接続の記述は、今回の実行指示として扱っていない。

現在の作業フォルダにはアプリコードがなく、接続済みGitHubから取得できた5件のリポジトリにも operation-instructions はなかった。対象コードと反映先の特定が必要。アプリの実行、権限テスト、コード修正、GitHubへのアップロードは未実施。本報告の設計上の懸念は、実装で確認された不具合ではない。

## 確認できた事実と修正

1. 参照資料2は2024年版を指定していた。国土交通省の現行掲載PDFは2026年6月26日最終改正版。v1.1では改正日、URL、第9条の3の掲載ページを更新した。
2. 同通達の第9条の3には、会社と運転者の変更記録、指示日時・運行管理者名、電子作成・保存の根拠がある。第7条1(2)への準用から、文字メッセージの既読だけで指示完了にしない設計は整合している。
3. 144時間の制限について、最初の勤務から最後の勤務までを確認する方向は国交省資料と整合している。通常の休息をすべて差し引く設計にはしない。
4. GitHub Pagesは静的ホスティングであり、Freeでは公開リポジトリが対象。有料プランではprivateからの利用も可能。資料のプラン確認の記述は整合している。
5. SupabaseではRLSと操作権限の設定が必要。service_role等の高権限キーをサーバー側に置く方針は整合している。

法令全条文、すべての例外、本件の具体的な電子携行方式の適否を確認し終えたという意味ではない。指定日を含むe-Govページの本文取得に制約があり、2026年10月9日時点の全改正を網羅した法令適合判定は行っていない。

## コード取得後に優先して検証する項目

| 優先度 | 設計から考えられる問題 | 検証・修正方針 |
|---|---|---|
| 高 | 版番号だけをロックしても、発行直前の下書き変更を検知できない可能性 | base_versionと下書きのrevisionをトランザクション内で照合し、審査した内容だけを発行する。同時発行で版番号の重複がないことを確認 |
| 高 | 「発行済み」「有効版」「実行完了」の区別が未定義 | 発行直後・通話前・確認前・新しい版の発行後をそれぞれ検証し、未完了の変更を通常実行可能と誤表示しない |
| 高 | 端末保存の成功がサーバー同期・会社保管の成功に流用される可能性 | IndexedDBへの保存、サーバー受信、会社写し、音声指示、ドライバー記録を独立して確認する。圏外入力は未送信と表示 |
| 高 | オフラインキャッシュが別アカウントから閲覧される可能性 | ユーザー・会社・運行別に保管し、ログアウトとアカウント切替時の隔離を検証。権限停止後の端末残存データの運用も定める |
| 高 | 保存期限が親運行の削除・添付Storageの削除で回避される可能性 | 親子テーブル、Storage、管理API、定期削除処理で保存期限と保留フラグを確認。保管前の運行も誤削除しない |
| 高 | 再送時に同じ操作IDで違う内容を送れる可能性 | 操作IDを利用者・操作・対象に紐付け、内容の不一致は拒否。再送で会社写しや記録が重複しないことを検証 |
| 中 | 入力項目に最初の勤務開始・最後の勤務終了が明示されていない | 出庫・帰庫とは別の予定／実績フィールドを確認。144時間ちょうど、超過、未入力、フェリー控除を検証 |
| 中 | 日付の解釈、時刻順序、うるう日で期間判定がずれる可能性 | サーバー時刻、JST表示、実日時を区別し、保存年数を単純な日数換算で短縮しない |
| 中 | 退職者・監査閲覧者の役割変更をクライアントだけで制御する可能性 | API、RLS、ビュー、ファイル取得で所属と有効期間を検証する。直接API呼出しによる発行・他営業所の閲覧を拒否 |

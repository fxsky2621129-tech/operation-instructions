# 運行指示書管理アプリ 設計仕様 v1.1（参照資料修正）
作成日：2026年10月8日／更新日：2026年10月9日／対象：一般貨物自動車運送事業の長距離フリー便

## 1. 対象と設計方針
日曜日又は月曜日に出庫し、金曜日又は土曜日に帰庫。出庫時に最初の荷物だけ確定し、以後は利用運送会社からLINE等で配車を受ける運用を対象とする。Androidスマートフォンと会社PCで共通のデータを閲覧する。
本書は実装仕様案であり、稼働済みアプリや法令適合の認証ではない。GitHubへの登録、外部サービスの契約・接続・公開は未実施。
GitHubはコード・変更履歴・ビルド管理。実際の運行データは認証付きクラウドDBに保存する。利用運送会社の荷物連絡を、自社運行管理者が安全な運行指示へ変換する。

## 2. 法的前提と実装上の対応
- 輸送安全規則第9条の3の対象は、第7条第3項に規定する業務を含む運行。自動点呼の有無や泊数だけで判定しない。本件では途中の業務前・後がいずれも対面等でできない勤務を含む前提で、運行指示書を作成する。
- 電磁的記録による作成・保存は解釈通達第9条の3の5で認められる。
- 変更時は会社側の写しへの記載、運転者への指示、運転者側の記載が必要。通達第9条の3の2に従い指示日時・運行管理者名を残す。
- 同通達第9条の3の4は「その他の方法」に第7条の解釈を準用する。第7条の解釈は直接対話できる方法を要求する。したがって、LINE文章・既読・アプリ承認のみを変更指示完了の条件にしない。電話又は直接対話できる音声通話で指示し、アプリに双方の記録を残す。
- 指示書と写しは運行終了の日から1年間保存する。アプリは終了から最低1年間の削除防止を実装し、運用上は3年間を初期保存方針案とする。点呼等の他帳票の保存要件は別に管理する。
- スマートフォンの携行では、最新指示書を通信なしで読める仕組み、会社側の常時閲覧、書面出力を設計要件とする。具体的な携行方式は本番導入前に管轄運輸支局へ確認する。電子作成・保存の許容だけで、任意のスマホ運用の適法性を断定しない。
- アプリは点呼を代行しない。実施済みの点呼記録への参照を保存できるが、荷物登録や確認操作を点呼とみなさない。

## 3. GitHubと外部サービスの構成
推奨構成案：React + TypeScript + ViteのPWA、GitHub、Supabase Auth/PostgreSQL/非公開Storage、承認処理用サーバーAPI。
PWAはスマートフォンのホーム画面から開く形式。GitHub Pagesを使う場合は公開される静的な画面とアプリコードだけを置き、実データ・PDF・添付画像は置かない。私有リポジトリでもPagesは原則公開される。アプリ利用者は個別アカウントでログインする。
会社名義のprivateリポジトリを新設する案を基本とし、既存の個人用勤怠リポジトリへの統合は前提にしない。仮リポジトリ名：operation-instructions。
DBには会社ID・営業所IDを持たせ、APIとDBの両方で所属・権限を検証する。ドライバーにGitHub編集権限を与える必要はない。
Supabaseの公開可能なキーはRLSと認証を前提に使用。service_roleやsecret key、GitHubトークンはスマホ・JavaScript・リポジトリへ入れず、サーバー側だけで管理する。
料金は契約・利用量・保存量によるため未確定。無料枠に本番の保存・バックアップ要件を依存させない。

## 4. 権限
| 役割 | できること | 制限 |
|---|---|---|
| ドライバー | 自分の荷物登録、変更申請、指示確認・記録、実績登録、自己のPDF閲覧 | 指示発行、他人の運行閲覧、確定版書換え不可 |
| 配車担当 | 所属営業所の下書き編集、情報整理 | 運行管理者権限なしでは正式発行不可 |
| 運行管理者 | 運行計画確認、指示発行、音声指示記録、修正版発行 | 過去の発行版の上書き・削除不可 |
| システム管理者 | 利用者招待、所属・権限設定、保守 | 管理者という理由だけで運行指示を発行できない |
| 監査閲覧者 | 許可された期間・営業所の閲覧と出力 | 編集・発行不可 |

共有アカウントは使用しない。運行管理者が休みの時間帯も対応できる担当体制を設定する。

### 法定項目
| 項目 | 入力・表示 |
|---|---|
| 運行開始・終了の地点及び日時 | 出庫地点・日時、帰庫地点・予定日時。確定度と変更履歴を併記 |
| 乗務員等の氏名 | アカウントと紐付く氏名。交替要員も登録 |
| 運行経路・主な経過地の発着日時 | 積地・卸地、主なIC/道路、主要経過地、到着・出発予定 |
| 注意を要する箇所の位置 | 高さ・重量制限、狭路、工事等。該当なしの場合も確認記録 |
| 休憩地点・時間 | 場所と開始・終了予定又は長さ |
| 運転者の運転・業務交替地点 | 交替あり／なし、ある場合の場所・予定 |
| その他安全確保に必要な事項 | 休息計画、悪天候、荷物の取扱い、緊急連絡等 |

### 管理・フリー便対応項目
運行ID、会社・営業所、車両番号、利用運送会社、荷主、配車連絡元、連絡を受けた日時、積卸住所、荷物名・重量・個数、予約時間、荷役方法、連絡先、受注資料、手積み手卸し等の附帯作業、入力者。
休息は休憩と分けて登録。拘束時間中の荷待ち・荷役・運転の計画を区別する。
変更理由、申請日時、発行者、発行日時、指示した日時・方法・相手、音声指示の要点、ドライバーの確認内容・日時、版番号、保存期限。
GPSは任意の補助。積卸住所や指示経路をGPS位置だけで代用しない。LINE画像の文字読取りは将来機能とし、読取り結果を自動で確定しない。

## 6. フリー便の計画方法
未決定の荷物は「未確定」として表示し、存在しない積卸先・時刻を作らない。ただし帰庫日時・経路・休憩等の必要項目をすべて空欄にした指示書を発行できる設計にはしない。
初回荷物の区間に加え、その後の待機地点、休憩・休息の予定、次回の会社への連絡時刻、次便未承認時の行動、帰庫の暫定計画を運行管理者が定める。
帰庫予定は日付の幅だけで済ませず、会社が合理的な暫定日時を設定し「暫定」と明示する。状況が変われば変更指示を行う。暫定値は実績値として扱わない。
未確定表示を許す入力欄と正式発行に必要な欄を分け、管理者が安全な計画を立てられない状態では発行を止める。この段階的な記載方式は法令上の免除ではなく、本件用の運用案。本番前に具体的な帳票例で確認する。

## 7. 通常の運用
1. 出庫前：運行管理者が初版を作成・発行。ドライバーが内容確認・端末保存。会社側に同版の写しを保存。
2. 次の荷物決定：ドライバーは安全に停車した状態で「荷物追加」。LINE文章の転記又は資料添付で下書き保存。
3. 会社確認：管理者が積卸時刻、経路、休憩・休息、帰庫予定、既存の勤務実績との整合性を確認。
4. 変更指示：管理者が修正版を発行し、電話等で直接指示。実際に指示した日時・担当者・要点を記録。
5. ドライバー記録：同じ修正版の変更内容を確認し「この変更内容を運行指示書に記録する」を押す。ドライバー別の確認イベントと携行版を保存。
6. 管理画面に「会社記録済み・音声指示済み・ドライバー記録済み・端末保存済み」を別々に表示する。
7. 実行：荷積み・荷卸・休憩・休息等の実績を登録。予定と実績を分けて表示。
8. 帰庫後：最終実績、未処理申請、全変更履歴を確認して運行終了。初版・全修正版・会社写し・ドライバー記録を保存。

「指示の理解とドライバー側記録が揃うまで通常の変更実行を完了扱いにしない」を社内運用ルールとする。ボタンの操作時刻は実際の通話時刻とは分ける。

## 8. 状態と更新の競合
変更申請：下書き→申請済み→審査中→差戻し／却下／修正版発行。
修正版：発行済み→音声指示記録済み→ドライバー記録済み。指示記録・ドライバー記録の順序は実際の手順を保持し、完了条件で揃ったことを判定。
運行：作成中→出庫前確認→運行中→帰庫確認中→保存確定。
下書きを何度変更しても発行済み版は変えない。発行時はDBトランザクションで全項目のスナップショット、会社写し、版番号を保存。
一つの変更で対象となる版IDを固定。ドライバーの確認はその版にのみ適用する。旧版確認中に新しい版が発行されたら、新版の確認が必要。
base_versionを申請と発行で照合し、競合したら差分を表示して再確認。操作IDで重複送信を防ぐ。発行時刻はサーバー時刻、実際の指示日時・実績日時は別フィールドにする。

## 9. 画面
### スマートフォン
ホーム：現在の運行、現在の有効版、未確認の変更、同期状態、最新保存日時、会社への電話ボタン。
大きい操作：「荷物を追加」「変更を報告」「指示を確認・記録」「運行指示書を表示」「実績を入力」。
未発行＝灰色、確認待ち＝黄、記録完了＝深緑、要対応＝赤。色だけに頼らず文字でも状態を示す。
運行指示書画面は予定・実績・未確定を明確に分け、全法定項目と変更履歴を表示。運転中の操作を避ける案内を入力画面に出す。
### 会社PC
運行一覧、変更申請一覧、音声指示未記録、ドライバー未確認、同期未完了、帰庫予定、保存帳票検索。
承認画面：旧版・新版の差分、追加荷物、勤務実績、注意事項、差戻し理由、発行・通話記録。
日付・営業所・ドライバー・車両・運行IDで検索し、単一運行又は期間まとめのPDF/CSV/JSONを出力。

## 10. 通信障害と緊急時
発行済みの全項目と変更履歴をIndexedDBに保存し、オフラインでも読める携行版を用意する。PWA導入だけで保存できるとみなさず、機内モードで起動・閲覧を検証する。
端末保存は消去・端末紛失の可能性があるため、会社の正式保管はDBと非公開ファイル保存に置く。PDFの端末ダウンロードも用意。
オフライン入力は未送信と明記。サーバー未達の承認・確認を完了表示しない。
通信不能で変更が必要な場合は停車して会社と直接対話し、会社は会社写しへ記録、ドライバーは携行版へ変更を記録する。ローカル記録と音声指示の実日時を保持し、復旧時にサーバー受信日時も追加する。
会社が確認できない、指示が不明、最新指示書を読めない場合は通常の変更運行を進めず、安全な場所で会社に連絡する。差し迫った危険回避は優先し、事後記録では遅延理由を残す。
本番前に電話が不通・スマホ故障・圏外・サーバー停止の各場合の連絡先と手順を決める。

会社写しとドライバー記録は同じ画面を共有するだけにせず、それぞれの記録を保存する。PDFは版ごとに固定し、最新版だけを再生成して過去を置き換えない。
監査イベントは通常の利用者によるUPDATE/DELETEを禁止。DB管理者でも改変が絶対不可能とは表現しない。別系統のバックアップ、操作ログ、アクセス制限で改変・消失を検知・抑制する。

## 12. 安全な計画を確認する機能
初期必須：必須項目、前後時刻、休憩と休息の区別、予定と実績の区別、未指示・未確認の警告、一の運行の期間の確認。
一の運行の期間は、出庫時刻だけではなく最初の勤務開始から最後の勤務終了までで確認し、144時間上限への接近・超過を表示する。フェリーの休息控除がある場合は根拠を記録し、任意の差引きを許さない。
日曜早朝開始→土曜夜終了は144時間を超え得るため、曜日だけで許可しない。
拡張：拘束・休息、連続運転、2日平均、2週平均、月・年の拘束、36協定・時間外の条件を既存勤怠データと連携する。
欠けた過去データがある場合は「判定不能」とし、問題なしと表示しない。運行指示書の予定入力のみで実際の改善基準遵守を確定しない。特例は会社の適用条件と根拠を設定してから実装する。

## 13. 保存・バックアップ
終了後最低1年を経過する前は、指示書・写し・関連変更記録をユーザーが削除できないようにする。3年保存は社内方針案であり、法定期間と表示を分ける。
日次バックアップ、別保存先への定期エクスポート、定期的な復元検証を運用に組み込む。帳票と履歴を一体で取り出せるようにする。
PDFを会社PCで速やかに表示・印刷できるようにする。PDF・JSON・CSV・添付一覧・版ハッシュを運行単位で出力する。
退職時はログイン権限を停止し、会社の保存記録を維持。監査・争議等の保留対象は保存期限後も削除を止める。添付に無関係な個人情報を含めない。

## 14. 実装順序
第1段階：個別ログイン・所属権限、運行作成、荷物申請、管理者発行、直接対話記録、ドライバー変更記録、オフライン閲覧、版別PDF、検索・保存・バックアップ。
第2段階：実績登録、計画と実績の比較、通知、勤務データ取込み、改善基準の判定。
第3段階：LINE資料の文字読取り、地点マスター、配車会社別入力補助、追加の監査集計。
実データなしの試作では「デモ・正式指示ではない」と表示する。認証・同期・権限・保管がない単体HTMLを本番の共同管理アプリと呼ばない。

## 15. 本番受入条件
- 他ドライバー・他営業所・匿名アクセスから実データを取得できない。
- ドライバーや配車担当がAPIを直接呼んでも正式発行できない。
- 変更内容の双方記録と直接対話記録が監査出力から確認できる。
- 発行済み版が訂正で上書きされず、旧版と新版の差分を出力できる。
- 旧版に対する確認が新版の確認に流用されない。
- 同時更新・二重送信・圏外復旧でデータを失わない。
- 最新保存版が機内モードで閲覧でき、未同期が明示される。
- 帳票には全法定項目、指示者・日時、版番号、双方記録が含まれる。
- 保存期限前の削除が禁止され、バックアップから帳票と履歴を復元できる。
- 未確定部分を含む具体的な初版例、携行・音声指示・障害時の手順を会社と管轄支局で確認している。

### API操作
| 操作 | 必須の確認 |
|---|---|
| 運行を作成 | 所属営業所、対象ドライバー、車両、必要項目 |
| 荷物申請を送信 | 本人又は所属配車担当、運行状態、基準版、重複操作ID |

発行・会社写しの作成・監査イベント追加は一つのDBトランザクションにする。ブラウザから発行済みテーブルを直接更新させない。
GitHub Actionsでは型チェック・本番ビルドと、必要な権限・版管理検証を行う。本番DBの変更は検証環境で確かめてから適用する。実データや秘密キーをActionsのログに出力しない。
GitHub Freeで公開Pagesを利用する場合は、画面コードを公開可能なものに限定し、公開用リポジトリを分ける構成も選択肢。privateリポジトリからのPages利用可否は契約プランで確認する。会社データの非公開性はDB・APIの認証で担保する。
